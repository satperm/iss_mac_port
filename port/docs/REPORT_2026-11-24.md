## The black screen after a load (#90, #92)

The first-start compilation is skipped once its done file matches. Metal keeps its own cache of compiled shaders
(per app, ~2 GB here). When that cache is lost, an OS update for example, or Metal evicting entries after a
day of test builds, the game compiles hundreds of pipelines when a save loads. Reproduced by moving the app's
Metal cache aside: 17 FPS, ~28 s of compile work in 5 s, 129 frames held (the black screen).

- **#90:** the done fingerprint includes the OS build. Each start builds a sample of 45 job file pipelines and
  times only the driver's part. The baseline is the same sample's time right after the last full compilation.
  More than 3x that compiles again. Warm 3.3 ms against a 3.4 ms baseline, cold 125 ms. It costs ~0.45 s per
  start before the menu. A full compilation takes 9-20 s with a warm Metal cache and ~2 minutes with a cold one.
- **#92:** after a full compilation, loading the village still built 426 graphics and 168 compute pipelines.
  Every one uses the same shaders as a job record; only the render state differs (target formats, blend,
  resource validity). These are now appended while playing to `learned-jobs.bin` in the cache folder (job
  format, deduplicated across starts, at most 32 MB) and built by the next full compilation. Cold Metal cache:
  65 held frames -> 1. FPS with learning on/off: truck 85.4 / 85.1. The game keeps producing new variants
  (594, +83, +167 in three 90 s sessions), so the file grows until the cap.

## What limits the 1080p frame (truck, M3 Max)

- **Main thread:** ~32% own work, ~40% waiting for the GPU particle chain (compute queue label idx 2, the label
  ~7 behind its target), ~9% waiting for label idx 0, ~13% on a lock, ~4% other sleeps (`TLG_WAIT_PROBE=1`).
- **Particle chain timeline** (`TLG_CHAIN_LOG=1`): 2.0-2.6 ms from the GPU command thread seeing a fence to the
  recording thread running it (graphics queued ahead), then 1-2 ms to GPU done.
- **Reordering does not help:** compute lane first 82.7, after 500 us 82.5, after 1500 us 84.4, off 84.6
  (truck, 2 x 60 s; branch `agent/acb-demand`). The game waits less but the graphics is recorded later.
- **Both CPU stages are on the critical path:** +200 ns a draw on stage A or B (~1.3 ms a frame) costs
  85.1 -> 79.2 / 80.0 FPS, ~60-70% of the delay reaches the frame (`TLG_STAGE_DELAY_*_NS`).
- **The GPU is busy too:** 13.7 ms of GPU work a frame (sum of intervals, vertex and fragment overlap) at an
  11.8 ms frame (`pass_profile.sh`). Biggest: compute 2.55 ms, G-buffer 1.48 ms, 2048x2048 shadows 1.23 ms.
- **Stage A hot spot removed, no gain:** `PendingWriteOverlaps` scanned ~140 entries in a third of ~10,000
  checks a frame (~13% of stage A). An interval map takes it out of the profile (stage A -6%), FPS unchanged
  (truck 85.6 -> 85.4, bridge 111.4 -> 111.1, village 77.2 -> 77.1; branch `agent/pending-writes`).
  The time saved becomes waiting.

## Afternoon

### The tightest stage: the Vulkan recording thread

`TLG_STAGE_DELAY_C_NS` (new, diagnostic) busy-waits per recorded command on `tlg:VkRecorder`, the thread that
replays the recorded commands into MoltenVK. At 200 ns a command (~13,000 commands a frame) the truck drops
85.8 -> 61.9 FPS, against 85.1 -> 80.0 / 79.2 for the same delay per draw on stage A or B. The thread is busy
~73% of the frame: draws ~20%, render pass starts ~14% (`beginMetalRenderPass`), push descriptors ~10%.

### #95: submissions without waiting

At each of ~77 submissions a frame the draw-recording thread waited for that thread to record everything
queued (`TLG_SYNC_STATS=1`: ~1.6 ms a frame on the truck), then submitted. Now the submission is a recorded
command: the recording thread waits for the host copies issued before it, ends the command buffer, submits
it and begins the next one; the command pool is only used on that thread.

### Closed without gain (branches kept)

- **The frame's present commands on the recording thread** (`agent/present-record`): removes the last two
  recorder syncs a frame, but Seattle 88.0 -> 85.2; the sync at the flip seems to pace the frame. It needed
  `WaitIssued`: a submission must not wait for a tick that is not yet submitted on the same Metal queue
  (GPU timeout and device lost without it).
- **Depth-only passes without a pixel shader** (`agent/depth-only-ps`): the shadow map's pixel shader
  discards (alpha test), so nothing changes.
- **A code-free state list for new players:** register values alone reproduce only 135 of 368 learned
  pipelines; descriptor data (user data, V#) is needed too. The learned records' shader code is byte for
  byte the job file's, so a list without code, restored from the player's own job file, would be possible.
  Shipping one is the owner's call.

- **Submission batch size** (`TLG_SUBMIT_DRAWS`, 64): 256 gave truck +0.5%, bridge -1.2%, village -0.6%; 512 worse
  everywhere (bridge 113.1 -> 103.8). 64 stays.
- **MoltenVK live resource checks off** (`MVK_CONFIG_LIVE_CHECK_ALL_RESOURCES=0`): truck 89.2 -> 88.0, Seattle
  unchanged. Stays on.
- **Push constant dedupe on the recording thread** (`agent/push-dedupe`): 62% of pushes are repeats, but FPS is
  unchanged (truck 87.9 -> 87.9, Seattle 84.4 -> 84.6, bridge 112.9 -> 112.8).
