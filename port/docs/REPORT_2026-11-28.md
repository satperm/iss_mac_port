Owner's targets: M3 Max a steady 60 at 1440p native and 4K upscaled, Pro class 60 at 1080p-1440p. Measurements on
the M3 Max with System Settings' Storage pane scanning in the background from ~01:00 (190% CPU, load ~10): runs
after that vary by up to 25%; only interleaved A/Bs with 3-4 runs each are compared.

## Where a 1440p Seattle frame goes (16 ms)

No single resource is full (GPU 57-64%, recorder 55%), yet the frame grows with the resolution:

- **Causal tests** (1 x 75 s each): half render size 61.9 -> 78.7 (+27%); +200 ns per recorded command 54.4 (-12%);
  +200 ns per draw in stage B 59.9 (-3%). GPU and recorder both set the frame: they run one after the other.
- **GPU timeline** (Metal System Trace, `tools/gpu_probes/gpu_union.py`, `gpu_gaps.py`): the GPU is busy 57% of the
  time. Once a frame it idles 2-4 ms at the same place, between the 1024x1024 depth-only pass (shadows) and the
  797x880 pass without attachments (260 of 265 big gaps); the rest is ~230 small gaps (<0.5 ms) between command
  buffers, ~4 ms a frame together.
- **Why:** the game's main thread spends ~55% of its time in its own wait for a command buffer context
  (`TLG_THREAD_PROFILE_MS=2 TLG_WAIT_PROBE=1`): the per-frame context's label lags by 1.0 (861 samples / 10 s), the
  small contexts' by 4.8 (717). Those labels are written when the GPU has finished the previous frame's buffers. So
  the game keeps one frame in flight, and a frame costs its own CPU work plus the latency of the previous frame
  through GPU command thread -> draw preparation -> Vulkan recorder -> GPU. The 2-4 ms GPU gap is that round trip.
- **What does not limit:** the guest never blocks in submit-done (`TLG_GUEST_IDLE_STATS=1`, new: 0.0%, 2-3 of 2,227
  calls a 5 s window); the display label is free when the GPU command thread reaches it (`WaitVoLabel` 0.00 ms);
  flips take 0.02 ms to free the previous buffer; MoltenVK already skips every repeated Metal state call (viewport,
  scissor, blend, depth-stencil, pipeline, cull: compared before encoding in `MVKCommandEncoderState.mm`), so the
  planned "redundant state" patch has nothing to remove.
- **Consequence:** at 1440p on a Max every millisecond of GPU work per frame comes back almost 1:1 (half size +27%),
  and so does latency removed from the chain. Throughput tuning of one stage alone does not.

## Tried, no gain (reverted)

- Skip the draw-pipe drain before the display-label wait when the label is already free: 62.8 / 62.1 (4 x 65 s
  interleaved). The wait moves to the drain at submission end (7% -> 26% of the GPU command thread), which the
  guest heap fix needs.
- Smaller first submissions (`TLG_SUBMIT_DRAWS` 64 / 32 / 16): 58.7 / 59.4 / 58.5 (3 x 65 s, noisy).
- Compute shader labels (`TLG_CS_LABELS=1`) show ~400 one-workgroup dispatches a frame (cs 5b1e2375 167, acb
  2d89965d 54, ...): the game's own work, and the labels themselves cost 30% FPS, so not measured further.

## 4K output with a render scale (the owner's "4K upscaled" target)

Seattle, native output 3840x2160 (`iss_native_output=4`), `iss_native_percent` = scale, 1 x 75 s:

| Scale (scene size) | Upscaler off | MetalFX |
|---|---|---|
| 50% (1920x1080) | - | 66.6 |
| 67% (2572x1448) | 61.2-61.4 | 51.9-52.3 (truck 55.7) |
| 75% (2880x1620) | - | 47.9 |
| 100% (3840x2160) | - | 33.8 (truck 31.4) |

- **There is no 4K upscale in this mode.** The native patch makes the game's output surface the scene size, so
  MetalFX runs 1:1 at the scene size (`MetalFX: temporal scaler 2572x1448 -> 2572x1448`): a temporal anti-aliasing
  pass, and the presenter stretches the result to the display. Only the original-output path (1080p) upscales
  with the HUD at full size. A real 1440p -> 4K upscale needs the native path to keep a 4K output surface behind a
  smaller scene: feature work, and the upscale itself would cost more than the 1:1 pass below.
- **MetalFX costs 3.1 ms of GPU a frame at 2572x1448** (Metal System Trace: PreProcessing 0.85, MidProcessing
  1.40, PostProcessing 0.89 ms), which is the 61 -> 52 FPS step. `TLG_ISS_DIAG` places the whole cost in the
  encode step (motion pass, flush, copy and UI redirection: none measurable); its CPU side is 0.06 ms
  (flush 0.010, queue lock 0.000, encode 0.049). `TLG_METALFX_TIMING`'s 1.19 ms (GPUEndTime - GPUStartTime of its
  command buffer) undercounts: use the trace.
- `TLG_RENDER_SCALE` (the launcher's render scale) is ignored with a native output: 4K output + launcher 67% =
  a full 4K scene (33.8 FPS). Only the in-game "Native render scale" applies there.
- For the target: on an M3 Max, 1440p native holds ~62 in Seattle (just above 60, p99 17.2 ms); 4K output reaches
  60 only at 50% with MetalFX (a 1080p scene) or ~61 at 67% without it.

## Pro class on this Mac (busy cores standing in for missing performance cores)

`hog N` spins N threads at the game's priority (scratch tool), Seattle/truck 1080p, 1 x 75 s:

| Busy cores | Seattle | p99 | Truck |
|---|---|---|---|
| 0 | 87.9 | 13.2 | 88.6 |
| 6 | 86.1 | 13.3 | 88.8 |
| 9 | 66.6 | 24.7 | - |
| 12 | 52.9 | 47.1 | - |

The port needs about six performance cores; with six free the frame rate does not move. A 6P + 6E M3 Pro
should be near the "6" row, a 5P one in between. The game thread's "busy" share falls from 84-87% to 63-69% with
the busy cores while FPS stays: much of it is the game's own rdtsc spin in usleep.

Shorter spins with 9 busy cores (2 x 70 s, alternated): defaults 70.9 FPS / p99 26.6 ms; game usleep sleeps
(`TLG_GUEST_USLEEP_SPIN_US=0`) 74.5 / 21.3; all short (`+ TLG_PIPE_SPIN_US=50 TLG_RECORDER_SPIN_US=20`)
75.7 / 20.8. On the free M3 Max (3 x 70 s alternated) all short costs ~1%: Seattle 86.5 -> 85.8, truck 88.7 ->
88.0, with ~20% less CPU in the game process. Defaults unchanged (no FPS regressions on the Max); a candidate
rule for Macs with 5 or fewer performance cores, to verify on such a Mac.

## 1440p at a 60 cap, camera turning

`TLG_FPS_LIMIT=60`, 100 s: 58.9-59.1 FPS, 25-28% of frames at 17-20 ms. The forced GPU keep-alive
(`TLG_GPU_KEEPALIVE=2`) changes little (59.0-59.1, 24-26% slow frames): not a clock-down. The turning view at
1440p runs at 60.2 uncapped, so a steady 60 there needs ~10% more headroom from the GPU and the recorder
together (the frame chain above).

## Render passes at 1440p (`TLG_PASS_STATS=1`, Seattle)

188 passes a frame; 159 a frame end in `FlushBarriers` (image barriers: `General -> General` memory barriers on
2-3 images 62/frame, colour attachment -> shader read 39/frame), 15 begin a new target, 8 end with a submission.
The barrier ends are the game's feedback loops (11-24 report): not a merge candidate.

## Launcher render scale with a native output (#158)

Fixed: 4K output + launcher 67% rendered the full 4K scene (33.8 FPS); now 2572x1448, 62.3 FPS.

## Attachment loads at 1440p (tile memory)

- Upper bound, every colour load DontCare (diagnostic, broken picture): Seattle 1440p 62.8 -> 66.7 FPS (3 x 65 s,
  every run).
- Only the loads that can go: a pass whose first draw is the game's full-screen vertex shader (b94242a8), no
  depth, one layer, no blending, all channels written, no discard, viewport and scissor over the whole target.
  27 colour attachments a frame qualify (of ~186 passes; 115 a frame have depth). FPS 62.7 -> 62.8: nothing.
  The cost is in the passes with depth, mostly the G-buffer pass that barriers split into ~14 parts a frame; those
  loads carry the pass on and cannot go. Reverted (branch not kept).
- "Hold frame rate 60" at 1440p, 60 cap, turning camera: 58.8 FPS, 26.8% frames >= 17 ms (off: 59.2, 21.8%):
  the game's quality control does not step in at 59 FPS.

## Recorder at 1440p (Time Profiler, 6 s, VkRecorder 3,714 samples)

Draws 27% (`MVKCmdDrawIndexed::encode` -> `finalizeDrawState`/`prepareDraw`, the AGX driver's encode), the
recorder's own spin 16% (idle), render pass begins 15% (`vkCmdBeginRendering`: 188 passes a frame), push
descriptors with templates 13%, `bindMetalResources` 5%, push constants 4%. No single cheap lever left; the
pass begins follow from the game's barriers.

## The biggest 1440p lever: passes ended by feedback barriers

- Upper bound, every colour feedback barrier (General -> General) keeps the pass open (`TLG_MAC_KEEP_FEEDBACK=1`,
  unsafe: may read stale pixels): Seattle 1440p **62.2 -> 69.5 FPS** (3 x 65 s, every run). That is the ~10% a
  steady 60 at 1440p needs.
- What they are (counter, 5 s): **~174 a frame are on an image the open pass renders to** (the game samples a
  target it is drawing into: G-buffer decals and similar), ~8 a frame on images the pass does not touch, none in
  passes with storage writes, none with a memory barrier.
- Keeping the pass open only for the untouched ones (images written before the pass, in an earlier Metal encoder,
  which Metal orders by itself) is safe but finds ~8 a frame: 185 -> 184 passes, no FPS change. Reverted.
- The real fix is reading the target from tile memory: framebuffer fetch (a sampled read of the target at the
  fragment's own pixel becomes a colour-attachment read; MoltenVK maps input attachments that are also colour
  attachments to Metal's `[[color(n)]]`). Needs the shader recompiler to recognise same-pixel reads of a bound
  target, plus the pass to keep that target as an input attachment. Multi-day, the largest known GPU+CPU win at
  1440p (fewer passes also means fewer pass begins in the recorder: 15% of its time). Proposed for the backlog.
