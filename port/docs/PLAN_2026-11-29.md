## Proposal: two Vulkan recorders (the 1080p and Pro-class lever)

At 1080p the recorder is the most sensitive stage (+200 ns per command: -26%), and since #162 also at 1440p
(-12%). It is one thread (`tlg:VkRecorder`) running the chunks in order into the current command buffer;
each submission (every 64 draws, at a pass boundary) starts a new command buffer, and MoltenVK encodes to Metal
as the commands are recorded (prefill). Command buffers are already independent in state, so alternate ones
could be recorded on two threads (one command pool each) and submitted in order. What has to stay ordered:
the non-GPU side effects the chunks run (deferred fence writes that free guest memory, host copies,
`TlgCopy::AfterCopies` callbacks): they would move to the in-order submit. Estimate 3-5 days with soaks; the
gain is bounded by the draw-preparation stage B (DrawRec ~55% busy at 1080p) and the GPU. Strategy item 6
("two recorders") in PERF_STRATEGY.md.

Caveat (re-measured 11-28): MoltenVK's own parallel mode, `MVK_CONFIG_PREFILL_METAL_COMMAND_BUFFERS=1` (a command
buffer encoded on its own thread), is still much slower than the default 2 (encode while recording): Seattle
1080p 73.5 / 74.2 vs 88.7 / 86.9, 1440p 60.5 / 61.1 vs 69.5 / 69.2 (2 x 70 s each, no crashes). It starts
encoding a buffer only when it ends, so the GPU gets its work later. Two recorders must keep encoding while
recording (mode 2 on both threads), or they lose the same way.
