## The black city (#100)

25 of the game's 71 world sections wait for install package 1, which a PS4 loads once the Blu-ray install has
finished. Nothing loads it here, so a save that wants the overcast "dismal" sky gets no time of day: Seattle stays
black. One instruction (eboot 0x3c3bf5) clears the wait, written only when 37 bytes match. Our CUSA00004 matches
like iss_pc's CUSA00223. `ISS_INSTALL_GATE_FIX=0` turns it off, `ISS_INSTALL_GATE_LOG=1` counts the waits (owner's
save after the tower fight: `0=46 1=25`). The owner's save was never black (that fight alone does not trigger it).

## Pipelines met while playing (driver pipeline cache)

Even with a warm Metal cache, every session the compiler threads spent ~14 ms per pipeline met in game
(Seattle walk: 250-280 pipelines, 3.5 s of thread time in two minutes), mostly MoltenVK converting SPIR-V to MSL
again. MoltenVK can keep those conversions in its VkPipelineCache, and the port saves it (`TLG_BP08`), but that had
been off since 2026-11-01 because starts hung. The cause: `vkCreatePipelineCache` compiled a Metal library for
every cached shader before returning (minutes with a cold Metal cache).

- `patches/moltenvk-1.4.2-lazy-cache-libs.patch`: a cached library compiles on first use
  (`MVK_TLG_LAZY_CACHE_LIBS=1`), and copies share their MSL (the six compiler threads' caches are seeded with
  copies: +3.4 GB before, +0.5 GB after).
- `MVK_CONFIG_SHADER_COMPRESSION_ALGORITHM=1` (LZFSE): 435 -> 106 MB on disk after the first-start compilation.

| Seattle walk (2 min) | ms a pipeline | worst frames (s) |
|---|---|---|
| off, 1st / 2nd session | 15.9 / 11.8 | 385, 246 / 429, 428, 323, 216 |
| on, 1st / 2nd session | 8.0 / 4.4 | 146, 55 / 178, 34 |

FPS unchanged (truck 88.1 / 88.3, bridge 113.9 / 114.1). Ten starts through ISS.app: no hang. Cold Metal cache:
the probe saw it (121 ms against 0.17), compiled again in 117 s, then played. Seattle 30 minutes through ISS.app:
89.1 FPS median, steady.

- **#103:** MoltenVK merged pipeline caches without any lock (our caches lack the internally-synchronized-merge
  flag) and never locked the sources, while the port merges caches compiler threads add to (seeding, the saver
  every 60 s). Now each source is merged under both locks (`scoped_lock`). Stress: saving every 10 s during
  three Seattle walks, no crash lines.
- **Memory** (footprint of both processes): Seattle second session off 7.46 GB, on 8.18 GB. GPU process after a
  first-start compilation: off 4.16 GB, on 5.48 GB. Sharing the main cache with the compiler threads (no seeded
  copies, branch `agent/shared-pipeline-cache`, needs a MoltenVK change to convert outside the cache lock)
  brought the latter to 4.91 GB but nothing in the second session: parked.
